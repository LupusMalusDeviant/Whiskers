# Configuration

Strongly-typed settings classes bound from configuration (env vars / `.env` / `appsettings` / the writable `agent-settings.json` and `app-settings.json`). Each maps to a section and is injected via `IOptions<T>` / `IOptionsMonitor<T>`. Binding is wired in [`Program.cs`](../Program.cs); the env-var names are documented in [`.env.example`](../../../.env.example). UI edits are written to `app-settings.json` (the last config layer, reload-on-change) by [`../Services/Persistence/AppSettingsStore.cs`](../Services/Persistence/AppSettingsStore.cs) so they apply live.

**`DataPathOptions`** is the one exception to the `IOptions<T>` pattern below: it centralizes every path under the data directory (`WHISKERS_DATA_DIR`, default `/app/data`) and is built at **bootstrap** — before the DI container exists — then registered as a plain singleton and injected directly. Consumers take it as an optional last constructor parameter (the container supplies the registered instance; an explicit path still wins, which keeps the test seams working).

## Files

| File | Section / purpose |
|---|---|
| `SecretSource.cs` | Reads a secret setting (R1-28): `NAME_FILE` (a Docker/Kubernetes secret file) wins over `NAME`; a configured file that is missing, unreadable or empty throws `SecretFileException` and stops the start. Used for `VAULT_KEY` (vault, backup encryption, audit chain) and `WHISKERS_DB_CONNECTION`. `ReadFile` serves settings without a plain variable: `WHISKERS_ADMIN_PASSWORD_FILE` stops the start too unless `AUTH_DISABLED` is set, while the admin it seeds does not exist yet (once it exists the file is not read, so it may be removed after the first seed). |
| `DataPathOptions.cs` | Central resolver for all data-directory paths (DB, JSON stores, DataProtection keys, `ssh-keys/`, `mtls/`, `backups/`). Root = `WHISKERS_DATA_DIR` (default `/app/data`). Built at bootstrap, injected as a plain singleton — **not** via `IOptions<T>`. R1-39: `AutoPatchNightlyJson` (`autopatch-nightly.json`, the last nightly AutoPatch cycle; not restored from a self-backup). R1-40: `NotificationOutboxJson` (`notification-outbox.json`, critical notifications waiting for redelivery; not restored from a self-backup). |
| `ServiceCollectionExtensions.cs` | DI registration helpers (RoadToSAP Phase 0), **not** a settings class: `AddSingletonWithInterface[AndHostedService]` collapse the concrete + interface-forwarder [+ hosted] idiom into one call; `AddInitializable<T>` registers a startup [`IInitializable`](../Services/IInitializable.cs) (unwrapping a mutation scope guard). |
| `GoogleAuthSettings.cs` | Google OAuth 2.0 credentials. |
| `OidcSettings.cs` | Generic OpenID Connect provider settings. |
| `DockerSettings.cs` | Docker connection defaults. |
| `AuditSettings.cs` | Section `Audit` (R1-23): `RetentionDays` for the audit log and MCP call history (default 365, never below 30). |
| `MetricsSettings.cs` | Metric collection cadence; `ScrapeToken` gates the Prometheus `/metrics` endpoint (disabled when unset). The retention keys of the same section are read by `MetricRetention` instead. |
| `MetricRetention.cs` | R1-55: retention per metric tier and of the alert history, in the `Metrics` section — `RetentionDays` (raw, default 7, 1–365), `Rollup10mRetentionDays` (30), `Rollup1hRetentionDays` (180), `Rollup8hRetentionDays` (730), `AlertHistoryRetentionDays` (30); 1–3650 days. A key from the environment (`Metrics__…`) or `appsettings.json` is read-only; the others are edited on the Settings page (gated `config.save`). |
| `HealthMonitorSettings.cs` | Health-monitor thresholds. |
| `ImageUpdateSettings.cs` | Image-update check cadence. |
| `AutoPatchSettings.cs` | Nightly security auto-patching (section `AutoPatch`): on/off, dry run, window hour, severity, limit, exclusions. |
| `CveMonitorSettings.cs` | CVE scan cadence. |
| `MattermostSettings.cs` / `MatrixSettings.cs` | Notification channel settings. |
| `OutboundGuardSettings.cs` | Section `OutboundGuard` (R1-54, INV-60): `Exceptions` to the notification channels' outbound guard — each an IP literal plus port, or a host name plus port plus its exact `Addresses`. Edited on the Settings page only (gated `config.save`); the denied ranges are fixed in code, not configured. |
| `TerminalSettings.cs` | Web-terminal settings. |
| `AiChatSettings.cs` | Read-only advisor chat (provider, model, key). |
| `AgentSettings.cs` | Acting-agent provider access + system prompt (UI-editable, reload-on-change). |
| `WhiskersPublicUrl.cs` | The configured address people open Whiskers at (`Whiskers:PublicUrl`, env `WHISKERS_PUBLIC_URL` in compose; R1-15). The only source of absolute links in outbound notifications (approval links) — never a request's host; an invalid value (not absolute http(s), credentials, query or fragment) is ignored. |
| `GuardrailPolicy.cs` | A single guardrail policy (restrictive-by-default), incl. the per-policy tool mode (deny/allow) and `RequireSecondApprover` (R1-15, PC-D4: nobody decides their own request, not even in the chat; optional in `guardrails.json`, off by default and left out of the stored policy while off). |
| `GuardrailConfig.cs` | The multi-preset wrapper: several named `GuardrailPreset`s + the active one (persisted in admin-only `guardrails.json`). `ActivePolicy()` never falls back to another preset: an active preset that does not exist yields `GuardrailPolicy.FailClosed()` (R1-12). |
| `DnsSettings.cs` | Section `Dns`: provider, allowed zones, default TTL and the provider token — since R1-29 kept in the vault and named by `ApiTokenRef`; a plaintext `ApiToken` is only a legacy value (moved at start) or one set by the environment, and the settings store refuses to write one. |
| `IntervalValidation.cs` | R1-41: the loop intervals — `HealthMonitor:CheckIntervalSeconds` and `Metrics:CollectionIntervalSeconds` 5–86400 s, `ImageUpdate:CheckIntervalHours` and `CveMonitor:CheckIntervalHours` 1–720 h (30 days; earlier versions accepted monthly checks, and it stays far below the ~49.7 days `Task.Delay` takes). `ValidateInterval` registers a check that runs in `IHostedLifecycleService.StartingAsync` (before any loop; deliberately not `OptionsBuilder.ValidateOnStart`, which would also make a reload throw): **only zero or a negative value stops the start** with an `OptionsValidationException` naming the key and where to fix it (such a value never worked — it spun the loop or stopped the host); a positive value out of range starts with a warning and is clamped to the nearest limit, so an upgrade cannot turn a configuration that ran before into a restart loop. The options themselves are not validated, so a later reload cannot make them throw inside a loop. A hand edit that does not bind (`"30s"`, `1.5`) does make the options monitor's `CurrentValue` throw; `EffectiveInterval` catches it, keeps the last valid interval and warns once, and the metrics loop (the only loop that reads its whole section each cycle) keeps its last valid settings the same way. `ValidateInterval` also registers the one `EffectiveInterval<T>` per interval (the `IntervalGuard` value — the configured value in range, otherwise the last valid one, at first the clamped one; thread-safe, read live, with its unit): all four loops wait it, and `/metrics` staleness thresholds (`IntervalValidation.CveCheckInterval`), the MCP CVE summary and the self-metrics read it, so a value such as `2147483647` hours never reaches a `TimeSpan` conversion and no threshold disagrees with the loop. `ThrowIfInvalid` refuses an out-of-range value when a settings section is saved (`AppSettingsStore.SaveSectionAsync`) with an `IntervalOutOfRangeException` (key, minimum, maximum), which the Settings page shows as a localised message. |
| `MetricAlertSettings.cs` | Thresholds for `high_cpu` / `high_memory` / `metric_anomaly` events (drive AI triggers). |
