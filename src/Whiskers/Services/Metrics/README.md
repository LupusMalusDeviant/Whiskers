# Services/Metrics

Metric collection, storage and querying (CPU, RAM, disk, container stats). The design **decouples the collector from where metrics come from** so a server can use live Docker stats *or* a push/scrape telemetry pipeline (VictoriaMetrics) without the collector caring, see [docs/ARCHITECTURE.md](../../../../docs/ARCHITECTURE.md).

A background collector samples on a schedule and writes time-series to SQLite ([`../Persistence/`](../Persistence/)); the query service reads it back for charts and reports.

## Files

| File | Purpose |
|---|---|
| `IMetricsSource.cs` | The abstraction the collector reads through, hides SSH/Docker vs. scrape behind one interface. |
| `IDockerMetricsSource.cs` / `DockerMetricsSource.cs` | Reads live metrics straight from the Docker engine (default source). |
| `IPrometheusMetricsSource.cs` / `PrometheusMetricsSource.cs` | Reads server metrics from a Prometheus/VictoriaMetrics endpoint (push/scrape source). |
| `PrometheusQueryClient.cs` | R1-58: `IPrometheusQueryClient` — a typed, cancellable instant query (`/api/v1/query`): `PromQueryResult` (success with labelled `PromSample`s, or a failure with a short reason that never names the endpoint) and `PromQueryResult.Parse`, which only accepts `"status": "success"` with a `vector` result (an error status, another result type or a misshapen field is a failure, never an empty result). 10 s per query, the caller's cancellation is thrown, a failed or unreachable endpoint is a failed result — as is every other exception (a cut-off body, `HttpIOException`, a sample time out of range); only the exception type is kept, never its message. `PrometheusMetricsSource` keeps its own scalar reads. |
| `DiskHealth/` | R1-58: optional disk-health readings (SMART, md, ZFS) from the hosts' metrics endpoints — see [`DiskHealth/README.md`](DiskHealth/README.md). |
| `MetricsSourceDispatcher.cs` | Routes each read to the source configured for that server (`ServerConfig.MetricsSource`); Docker is the default and fallback, Prometheus is opt-in. |
| `MetricsCollectorService.cs` | Background service that samples all servers on a schedule and persists the time-series (incl. host root-filesystem usage via `df`). Also emits `high_cpu` / `high_memory` / `high_disk` (server-level) / `metric_anomaly` events (thresholds from `MetricAlertSettings`) which drive [AI triggers](../Agent/Triggers/). R1-56: the three threshold alerts run on the host rules' `BreachTracker` ([`HostLoad/`](HostLoad/)) — raised once per breach after `SustainedMinutes` of elapsed time, closed by `<kind>_recovered` after five minutes below the threshold minus 5 points, `CooldownMinutes` the least gap between two breaches of one series; `metric_anomaly` (a point-in-time outlier) keeps re-firing after `CooldownMinutes`. A series without readings for longer than `BreachRules.GapToleranceFor` the interval (3 min, or three intervals when longer) — a failed stats call, a host missing from the system-info read (its disk is part of that gap), a `df` that stopped answering, a server whose container listing keeps failing (one gap for its containers) — raises one `metrics_gap` (`SeriesGapTracker`) and `metrics_gap_recovered` when readings are back; its breach starts again, and a raise the reset ends is closed with `<kind>_recovered` marked unconfirmed (one rule for every reset, `BreachTracker`). Review round 1: a container is forgotten only when a listing its server answered no longer has it (`FleetContainerListing.MayPruneStateFor`) — a failed listing keeps its breach; a container that is gone (stopped, removed, recreated) has its open alerts and gap closed, unconfirmed (review round 3); a configured but disabled server keeps its containers' state like a paused one. A cycle that starts more than the tolerance after the last one was held up: a log line, never one gap per series — its open alerts are closed by the gap rule. A paused server (`ILoopSuspensionService`) and a `df` that never answered since the start raise no gap. The open threshold and host-load breaches are kept in `alert-breaches.json` (`IAlertBreachStore`, `AlertBreachStore.cs`: written when they change, read once at the first cycle), so a restart resumes them — not raised a second time, closed with their recovery; a file that cannot be read is logged and the alerts are raised again if the breach goes on. The file also names the server of each container with a kept breach (so a listing failing in the first cycle keeps it) and seeds the disks read before; the state of a server no longer configured is closed (unconfirmed, `BreachTracker.Close`, `SeriesGapTracker.Close`, `HostLoadEvaluator.Close`) and dropped. A close no reading confirmed carries `NotificationEvent.RecoveryUnconfirmed` (titled "… closed — recovery not confirmed", Warning) and sets no minimum gap. Its clock is an injected `TimeProvider` (`CollectMetricsAsync` is driven by a fake clock in `SustainedAlertTests`). R1-41: its cadence is the shared `EffectiveInterval<MetricsSettings>` (a reloaded value outside 5–86400 s keeps the last valid one), the same value its self-metrics report as the loop interval. Follow-up (2026-11-03): the file also keeps the announced `metrics_gap`s (optional `Gaps`), closed once after a restart; the API-latency and baseline alerts of a removed server are closed too. |
| `IMetricsQueryService.cs` / `MetricsQueryService.cs` | Queries historical container/server metrics. R1-55: a `MetricPoint` carries the sample-weighted average (`Value`), the true maximum (`Max`) and its sample count; the range picks a tier (raw for 1 h/6 h, 10 min for 24 h, 1 h for 7 d/30 d — the coarsest whose window still gives 100 points) and is stitched at window boundaries — coarser tiers for the older part, finer tiers and the raw tail for the part newer than the tier's watermark — then thinned to 100 points keeping each point's maximum. `MetricSummary` gives the weighted average and peak of a whole history. |
| `MetricTiers.cs` | R1-55: the fixed tiers (10 min, 1 h, 8 h), window alignment and the watermark ids. |
| `IMetricRollupService.cs` / `MetricRollupService.cs` | R1-55: rolls closed windows up into the tiers (`ContainerMetricRollups`, `ServerMetricRollups`: average, maximum and sample count per series), one transaction per batch together with the tier's watermark (`MetricRollupStates`), so a crash neither loses nor double-counts a window; and applies each tier's retention — never deleting what the next coarser tier has not committed — plus the alert history's own retention. Run by the collector after its samples are saved. |
| `MetricSeriesKinds.cs` | R1-55: the container and server series over their raw and roll-up tables, shared by roll-up, retention and query. |
| `IMetricRetentionService.cs` / `MetricRetentionService.cs` | R1-55: the retention of each tier and of the alert history (`MetricRetention`, keys in the `Metrics` section). A key set by the environment or `appsettings.json` wins and is read-only; the others come from `app-settings.json` (the Settings page's gated, audited `config.save`) or the default. A value that does not parse never throws. |
| `MetricPeriods.cs` | The history ranges of the charts and MCP tools: `1h`, `6h`, `24h`, `7d`, `30d`. |

**Collector cycle (R1-55).** After each cycle's samples are saved, the collector rolls up the windows that closed (every 10 minutes; every cycle while the upgrade's first pass catches up) and, at most hourly, applies retention — in a step of its own, on the retention the cycle read, so neither a failed collection nor an unreadable `app-settings.json` holds retention up (R1-41 leftovers: the prune no longer re-reads the section, and a first read that fails starts on the defaults). The daily audit retention (R1-23) runs in the same step; R1-55 was built on top of it. The whole step — roll-up, metric and alert-history retention and the audit retention — runs only while `Metrics:Enabled` is true, as the prune did before.

**Clock set back.** If the host clock is corrected backwards after windows were rolled up, the first tier's watermark lies ahead of the clock. The roll-up never moves a watermark back (that would rewrite committed windows): it pauses, with one warning, until the clock passes the watermark again; meanwhile no tier below such a watermark is pruned, and a query serves the finer tier — down to the raw samples — from where it is complete instead of stopping at the watermark, so charts keep showing the data since the correction without duplicates. Samples taken between the correction and the moment the clock passes the old watermark are never rolled up; they stay in the raw tier for its retention and are then gone from the long view (the windows there hold the readings from before the correction). The warning is said once per episode — also when the clock was set back while Whiskers ran (a roll-up or prune schedule ahead of the clock counts as due).

*Manual way out* (Whiskers never rewinds by itself — that rewrites committed windows): if the clock was far ahead, the pause lasts as long. To end it, stop Whiskers (or accept that one cycle races you), then in **one transaction** delete, for the affected kind (`container` → `ContainerMetricRollups`, `server` → `ServerMetricRollups`), the rows of `MetricRollupStates` whose `Id` starts with `container/` (or `server/`) and the tier rows with `WindowStart >= ` the current time floored to 10 minutes; for example on SQLite: `BEGIN; DELETE FROM MetricRollupStates WHERE Id LIKE 'container/%'; DELETE FROM ContainerMetricRollups WHERE WindowStart >= '<now floored to 10 min, UTC, as stored>'; COMMIT;`. The next cycle rebuilds the tiers from the oldest raw sample still kept (rows already there for those windows are replaced, not added). Windows older than the raw retention keep what they had, except that the oldest window of each tier is rebuilt from whatever of its finer input is still kept and may then hold fewer samples. Two more costs: a deleted window whose raw samples are already pruned is gone for good, and raw samples still stamped with the old, fast clock (ahead of the real time) are rolled into the rebuilt windows together with the new ones, so those windows' counts overlap. On PostgreSQL the identifiers need quotes (`"MetricRollupStates"`, `"ContainerMetricRollups"`, `"Id"`, `"WindowStart"`). Take a backup first.
