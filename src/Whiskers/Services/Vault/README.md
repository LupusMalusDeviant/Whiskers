# Services/Vault

An **encrypted-at-rest secret vault**. Stores secrets (per-container secrets, API tokens) with **authenticated encryption (AES-256-GCM)** in `/app/data/vault.json`. The master key is derived from `VAULT_KEY_FILE` (a secret file, wins) or the `VAULT_KEY` environment variable via **PBKDF2-HMAC-SHA256 (600k iterations)** over a random, persisted per-vault salt (`VaultData.KdfSalt`).

Each secret is stored as `g1:` + base64(`nonce ‖ tag ‖ ciphertext`). The GCM authentication tag makes tampering detectable — a modified `vault.json` fails to decrypt instead of yielding attacker-influenced plaintext.

**Key check (R1-28, INV-54):** `VaultData.KeyCheck` holds a fixed text sealed with the derived key. At start the key must open it — or, on a vault written before R1-28, one of its GCM entries (the check is then added). Otherwise `KeyState` is `Wrong`: `IsEnabled` is false, nothing is read, written, deleted or migrated, and `vault.json` is left byte for byte as it was. `KeyState` is `NotConfigured` without a key and `Verified` with the vault's key. A configured `VAULT_KEY_FILE` that cannot be read stops the start (`SecretSource`).

**Migration:** legacy entries written by the previous unauthenticated AES-256-CBC scheme (key = `SHA256(VAULT_KEY)`, no salt) are re-encrypted to GCM on the first `InitializeAsync` after upgrade, all or none, after an untouched copy `vault.json.legacy-cbc.bak` is written. A vault of legacy entries only carries no proof of the key, so every entry must decrypt to valid UTF-8 — a padding that fits is not enough — or the vault is locked as `Wrong`. A locked vault lists no entries and no expiring secrets.

**Recovery:** if a legacy vault was converted under the wrong key (only possible when every legacy entry happens to decrypt to valid text under it), every later start with the right key reports the vault as locked. Stop Whiskers, replace `vault.json` with the recovery copy `vault.json.legacy-cbc.bak` (or the newest `vault.json.legacy-cbc.<time>-<n>.bak`), set the right `VAULT_KEY` and start again; the conversion then runs with the right key. The copy is written to a temporary file, flushed and moved into place, so it is complete or absent; an existing copy is never overwritten — one that differs from the current file (cut short, or from another vault a restore replaced) stays, and the new copy gets a new name. It holds the old unauthenticated CBC ciphertext and travels in every self-backup: delete it once the converted vault has been checked (its secrets read correctly). When no copy can be written nothing is converted (the salt of a vault that had none is still saved).

An **empty** vault (no entries) carries nothing that could prove a key, so it accepts the key it is first started with and seals its key check under it; to re-key an empty vault (or one locked by a mistyped key before anything was stored), stop Whiskers, delete `vault.json` and start with the right key. A vault whose key check or every entry was altered locks even with the right key — the only remedy is to restore `vault.json` from a self-backup. See [ADR 0001](../../../docs/adr/0001-vault-aead-gcm-pbkdf2.md).

**Concurrency:** the reads (`ListSecrets`/`GetSecret`/`GetExpiringSecrets`) run under the same lock as the writers (`SetSecretAsync`/`DeleteSecretAsync`), so a lookup or listing never races a concurrent set/delete. Writes are copy-on-write: a change is published only after `vault.json` is written, so a failed write leaves the live vault unchanged. Set/delete are `vault.secret_set` / `vault.secret_delete` (Admin, R1-11).

## Files

| File | Purpose |
|---|---|
| `IVaultService.cs` / `VaultService.cs` | AES-256-GCM secret vault; PBKDF2-derived master key from `VAULT_KEY_FILE`/`VAULT_KEY` (+ persisted salt), key check at start (`KeyState`), secrets stored encrypted at rest in `/app/data/vault.json`; migrates legacy CBC entries behind a recovery copy. R1-29: `AdoptLegacyCredentialAsync` stores a credential that a file already holds in plaintext, only under a fixed migration key (`CredentialRefs.IsMigrationKey`), and confirms it by reading vault.json back and decrypting it (a private check; the adoption call itself only answers whether a fixed migration key holds the given value, and only the start-up migration calls it — `CredentialAdoptionCallersTests`). "On disk" means the file as the operating system presents it: the JSON stores do not flush to the device yet, so a power loss right after the migration is the durability gap of R1-35. |
| `VaultBackedSettings.cs` | R1-30: which settings properties are kept in the vault (notification channels, AI chat, agent), their vault key names (`<Property>Ref` in the file; a new key per save, a fixed `:migrated` key for the migration) and `SecretFieldChange` (keep / set / clear / move, decided against the stored section under the store's lock; keep never writes a plaintext value). |
| `VaultSecretsPostConfigure.cs` | R1-30: binds the vault-backed properties from the vault when the options are bound (`AddVaultBackedSecrets<T>`, registered before the log redaction's post-configuration); a key in a disabled or locked vault, or a missing entry, reads as unset and is logged. `IVaultBackedOptionsCache` drops the cached options after the vault started. |
| `VaultBackedSettingsSave.cs` | R1-30: the editors' save — new values (and legacy plaintext that moves) to the vault under new keys (`vault.secret_set`), then the sections rebuilt under the lock (`config.save` / `config.agent`), then the replaced keys removed (`vault.secret_delete`); a failed or refused settings write removes the new keys; without a usable vault a save that would store a value is refused before anything is written. |
| `CredentialRefs.cs` | R1-29: vault keys of the infrastructure credentials (cloud API key per server, DNS token): a new key per save, one fixed key per credential for the migration. |
| `CredentialVaultMigration.cs` | R1-29 start-up migration (`IInitializable`, order 55): moves plaintext cloud API keys (servers.json) and the plaintext DNS token (app-settings.json) into the vault. Each is stored, read back from disk and compared before its file names the vault key instead; an interrupted run finishes at the next start, a run without a usable vault changes nothing and keeps the credentials usable. Not a gateway mutation: it only uses the narrow adoption calls above, never a general vault or settings write — so it leaves no R1-22 configuration-change history entry; its log lines say what moved. A file that cannot be rewritten keeps its plaintext (still usable, retried at the next start) without stopping the start. When the fixed migration key already holds a different value, the migration leaves the plaintext and logs it; a later save of that server or of the DNS panel moves the plaintext under a new key, and the stale `:migrated` entry stays as an unused encrypted secret that can be deleted on the Vault page. A section naming a vault key and also holding a plaintext token (only by hand editing) is reported as plaintext but not migrated — the reference wins; a save of the DNS panel drops the plaintext. The audit diff (R1-22) shows `CloudKeyRef` as it is (a vault key name carries no secret); `ApiTokenRef` and the plaintext fields appear only as fingerprints. A token set by the environment (`Dns__ApiToken`) is not read by the migration (it reads app-settings.json only) and is never moved. R1-30: also moves the notification/AI credentials of app-settings.json and the agent's API key of agent-settings.json (also while the agent module is off), and finally drops the cached vault-backed options so they bind again with the vault started. |
