# Services/Onboarding

**One-click server onboarding** into the zero-SSH-key managed stack. Starting from a single SSH bootstrap connection (the only time SSH is used), the orchestrator installs Tailscale, deploys telemetry and the mTLS Docker proxy, issues certificates, and switches the server to mesh + mTLS, with live progress streamed to the UI.

The bootstrap authenticates with **either an uploaded SSH key or a transient root/SSH password** (fed to `sshpass` via the `SSHPASS` env var, never persisted, `ServerConfig.SshPassword` is `[JsonIgnore]`). On success both are dropped: the password is cleared by a store write of a clone of the record the run holds (contract 0018 A6, never by editing an instance the store may share) and the key deleted from disk (`IServerConfigService.DeleteSshKeyAsync`), so **no standing credential remains**. Before its first command every run (a retry included, which reads the record again) reports the SSH destination and the credential the bootstrap uses — „Passwort" or the key file name, flagged when the file is missing, never a value (contract 0018 A5, `OnboardingRetryTests`); the executor's precedence (password before key) is unchanged. Reachable from the server add/edit dialog (**„Speichern & Onboarden"**) or the per-row onboarding button.

**Contract 0018 (PR 2).** Step order: `CloudBootstrap` (only with a cloud bootstrap) → `HostKey` (every SSH record, before the first command: pins the host key through `Services/Server/SshHostKeyPins`, a mismatch stops the run, no pins service fails closed, INV-63) → the existing steps → `BootstrapCleanup` (only after an injected key: removes the bootstrap line, then the sealed key; a failed removal fails the run and keeps the key, INV-64). A run that fails after the injection returns `StandingBootstrapKey` and a warning; the Servers page offers *Remove bootstrap access* (an abandon that runs only `BootstrapCleanup`), and `server.remove` runs the same removal first; over SSH both check the host key before the removal command (both verify a known key; abandon refuses without one and points to the resume, remove names the dead line). The Tailscale auth key is read from the vault by reference (`Onboarding:Tailscale:AuthKeyRef`, set in *Settings → Onboarding*) and reaches the host only through the secret channel, never on a command line. A cloud bootstrap started by a non-interactive principal needs a human Admin's approval (`CloudBootstrapRule`, bound to the VM's id, name and IP). The service itself refuses a run without a bootstrap on a record that carries an injected bootstrap key and no host-key pin (the VM may still be in rescue; a first contact could pin the rescue system's key) and points to the rescue resume or the abandon — the Servers page's `RescueResumeForced` is no longer the only guard.

**Contract 0018 (PR 3, part E).** The MCP tools `add_server`, `onboard_server` and `get_onboarding_status` (`Mcp/Tools/ServerTools.Onboarding.cs`) use the same services. `onboard_server` runs with what the gateway decided (`MutationScope.DecidedTarget`: the server, its mTLS state and the host it reached), on a token bound to the 30-minute gateway deadline rather than the request. Every run, from any surface, is recorded once it holds the host lock in `OnboardingRuns` (`IOnboardingRuns` / `IOnboardingRunRecorder`): the latest run per server in memory — operation id, start, current step, the last 200 progress lines, the Tailscale login link and the result — which `get_onboarding_status` answers (Admin only, D5).

See [docs/architecture/ARCHITECTURE.md](../../../../docs/architecture/ARCHITECTURE.md) > *Onboarding a new server* for the full step sequence.

## Files

| File | Purpose |
|---|---|
| `IOnboardingService.cs` / `OnboardingService.cs` | Orchestrates onboarding into the Tailscale + mTLS-proxy + telemetry stack, end to end, reporting progress (incl. surfacing the Tailscale login link in the app). Returns a step-tracked `OnboardingResult`. |
| `OnboardingRuns.cs` | Contract 0018 part E: `IOnboardingRuns` (read: `Latest(serverId)`) and `IOnboardingRunRecorder` (the service's side) over one in-memory registry; the latest run per server, its progress (≤200 lines), login link and result. No persistence: a restart forgets the runs (a standing bootstrap key is still reported from the record). |
| `ScrapeConfigEditor.cs` | Step 8 without Python (contract 0017 I1): the scrape config is read base64 from the Whiskers host, the node_exporter target is inserted in C# under the first `static_configs:` (the rest of the file kept line for line), and written back as root through `WriteFileAsRootB64` (`sh` when root, else `sudo sh`, like the CA steps; decoded into a temporary file first). The read-modify-write is serialised by a static gate, and invalid UTF-8 fails the step. Server id and address are double-quoted YAML scalars from YamlDotNet's emitter; the result is parsed again and must carry exactly that target. A target already present for the address changes nothing; a file without `static_configs:` is left alone with a warning. |
| `OnboardingResult.cs` | The `OnboardingStep` enum + result record (completed steps, failed step, actionable German hint per step). Every step is idempotent → a re-run after failure resumes safely (W3). |
| `IServerRegistration.cs` / `ServerRegistration.cs` | Contract 0018 part B: registration from name + public IP (`server.create`). The address must be a literal IPv4/IPv6 (no zone id); a cloud VM is found by exact public IP in exactly one stored credential and bound as `CloudProvider` / `CloudServerId` / `CloudKeyRef` (no name match, two hits refuse). |
| `ICloudBootstrap.cs` / `HetznerRescueBootstrap.cs` | Contract 0018 part D: step `CloudBootstrap` for `BootstrapMethod.HetznerRescueKey`. Acts only on the bound VM still holding the record's IP (running, unpinned, not bound twice; another VM name only with `confirmVmName`). Generates an ed25519 key in a memory-backed directory (sealed, plaintext removed), creates a project key `whiskers-bootstrap-{id}-{8 hex}`, enables rescue with it (the rescue root password is discarded unread), reboots into rescue, reads the host keys from the disk (pin source `RescueDisk`), appends the public line to root's `authorized_keys`, leaves rescue and deletes the project key. Any failure after rescue was enabled deletes the project key, disables rescue and resets the VM once. Resume reuses the sealed key; a missing key is refused and points to abandon. |
| `RescueCommands.cs` | Pure command builders for the rescue session and for `BootstrapCleanup` (remove every `whiskers-bootstrap-{id}-` line, read back); only code-owned values reach the shell. |
| `OnboardingCommands.cs` | Pure, unit-tested command/config builders (`OnboardingCommandsTests`): user input only reaches the shell through the strict `Slug` allow-list or base64; the tailnet IP passes only as a normalised IPv4 literal (`TailnetIPv4`: `AddressFamily.InterNetwork`, then `ToString()`; an IPv6 zone id such as `fe80::1%';…` is refused), and only that normalised value is used afterwards. `ReadFileB64` reads a code-owned file base64-encoded. R1-58: `NodeExporterCompose` (a copy of `deploy/telemetry/host/docker-compose.yml`) enables the textfile collector on `/host/var/lib/node_exporter/textfile_collector` through the existing read-only `/:/host` mount, for the optional SMART readings. |
