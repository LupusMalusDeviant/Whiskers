# Services/Docker/Operations

Internal collaborator classes behind the `DockerService` facade (see [`../README.md`](../README.md)). Each class owns one slice of the Docker operations surface; all are `internal sealed`, constructed by `DockerService` itself (no DI registrations), and share the facade's `ILogger<DockerService>` category plus a single `MemoryCache` instance so runtime behaviour is identical to the pre-split god class.

## Fleet-wide listing

`ListAllContainersDetailedAsync` returns the containers of every enabled Docker server **plus which servers
answered** (`FleetContainerListing`). The plain `ListAllContainersAsync` is a thin wrapper over it. Callers
that keep per-server state across cycles (log watermarks, previous container states, cooldowns) must use the
detailed variant: an unreachable host and an empty host both produce an empty list, and dropping state for
the unreachable one silently re-baselines it on recovery.

## Files

| File | Purpose |
|---|---|
| `ContainerOperations.cs` | List/inspect containers, stats (with 3 s cache), logs, start/stop/restart/remove, env inspection; also hosts the internal Docker-stats JSON DTOs. R1-41: the fleet listing's per-server timeout (`PerServerTimeout`, 8 s) bounds the wait for the client and for a budget slot as well as the request — running out in the request is that server's timeout, running out while queued for a slot is reported as `FleetServerFailure.NotAsked` (Whiskers' own saturation, no evidence about the server), the caller's own cancellation stays a cancellation; the state and configured-image inspects take the caller's token. Follow-up (2026-11-03): a fleet listing failure after the per-server deadline reads "Timed out" only when the deadline caused it (a cancellation or timeout in the chain); another error keeps its own reason. |
| `ContainerLifecycleOperations.cs` | Create from a `DeploymentRequest`, recreate-with-rename-fail-safe, and the C12 update-rollback (snapshot capture + rollback to the old image). When the new container's create, network connect or start fails, both restore the previous container through `ContainerRestore` (1.0.1). |
| `ContainerRestore.cs` | `ContainerRestore.RestorePreviousAsync`: after a failed recreate or C12 rollback, force-removes the container the attempt created **first** (it holds the service's name; renaming the previous one back before that answered 409 and left the service down — 1.0.0 review, Fleet HIGH 4), then renames the previous container back and starts it. When the create call itself failed without a definite refusal (not a 4xx `DockerApiException` — its answer possibly lost after the daemon made the container), the container holding the name is looked up (`FindByNameAsync`) and removed only if it is not the previous one, was created from the attempt's image and was never started (state `created`); someone else's container, or a started one, is never removed. `RecoverFailedStashAsync`: the rename of the previous container out of the way failed — it is started again if it ran before the attempt (from the inspect/listing, not from the stop's answer), and the attempt throws with the name the daemon lists for it. `RemoveCreatedAsync`: a C12 rollback with no previous container removes the rollback container it created (or, the create's answer lost, the one found under the same guards) only in an allowed state (`created`, `exited`, `dead`) and without force, so the daemon refuses (409) one that started meanwhile; any other state (running, paused, restarting, unknown or unreadable) is kept and the rollback throws with it. A container found by the lost-create lookup is likewise removed without force; only a known created id is force-removed. Whether the previous container ran is `ContainerRestore.WasRunning` (running, paused, restarting) or a stop that reports it stopped something. A restore step that fails is thrown (`InvalidOperationException` naming the previous container's current name and whether it runs, with the attempt's and the restore's errors inside), never only logged. `IContainerRestoreSteps` is the seam over the six Docker calls (find by name, read state, forced remove, non-forced remove, rename, start), `DockerClientContainerRestore` the production implementation; only `ContainerLifecycleOperations` calls the restore or constructs it (pinned by `MutationGatewayCoverageTests.Only_the_update_and_rollback_restore_drive_the_restore_steps`; behaviour: `ContainerRestoreTests`). The wiring inside `ContainerLifecycleOperations` has no in-process test: the test project loads Testcontainers' Docker.DotNet fork, and driving the real client there ends in a `MissingMethodException`. |
| `ImageOperations.cs` | Pull images (with robust repo/tag/digest reference parsing) and read image digests. R1-41: `GetImageDigestAsync(…, ct)` and `GetImageContractAsync(…, ct)` pass the caller's token to the inspect and the slot wait; a cancelled caller gets the cancellation, not `null`. |
| `NetworkOperations.cs` | List/create/remove Docker networks, connect/disconnect containers. |
| `HostShellOperations.cs` | SSH-free host shell via one-shot privileged `nsenter` helper containers, including the labelled-leftover sweep. The timeout and the caller's token (R1-38) both kill the helper; it is always removed afterwards. R1-57: the timeout is one deadline from getting the client through the image check/pull, create, start, wait and log read; every Docker call is awaited against it (`Within`), also one that ignores its token. Kill and remove hold the caller for a clean-up budget of their own (5 s) after it, so a caller has its answer at most timeout + 5 s after the call; a clean-up not finished by then goes on in the background with retries (up to 2 min, each attempt at most 5 s; every retry asks for the server's client again, which is a new one only when a reconnect replaced the run's), and a create given up on — or failed — whose answer still arrives has its helper removed. Clean-ups and sweeps run without the caller's execution context, so they are exempt from the emergency stop (stopping our own helper is what a pause wants). Every helper carries `serverwatch.hostshell.deadline` (its latest end, Unix seconds). The sweep (own 30 s budget) removes a labelled helper — stopped or **running** — more than a minute past its label; without a readable label, a stopped helper older than 30 s, while a running one (an older version's) is left alone. It runs with a host-shell call on the server (at most every 5 min), and is scheduled past the label (one per failure; one due shortly before a pending one is left to it) when the background clean-up gives up or a create never answers, retrying for up to an hour while the server cannot be reached; a helper left behind by a Whiskers restart, or by a longer outage, waits for the next host-shell call on that server. The label is Whiskers' wall clock, written and checked on the same clock: only a forward step of it between the run and the sweep (an NTP correction, a restart with a corrected clock) could remove a helper still in its run. A timeout that is not finite and positive is refused (`Utils/ExecutionTimeout`). A stop before the start request reads "did not start"; from it on "effect unknown" (also a Docker error after the start request); after the exit "exit code N, output not read" (exit code -1 on the result). CodeQL #23–#26: a secret the command names (`Server/HostCommandSecrets`) is the helper's environment (`Env`), never part of its `Cmd`. |
| `HostShellDocker.cs` | `IHostShellDocker`: the Docker calls of the host shell, one per step, and `DockerClientHostShell`, the production implementation over `DockerClient`. A seam so the deadline logic does not depend on the client library and tests can stall any single step (`HostShellDeadlineTests`). Only `HostShellOperations` calls it or constructs `DockerClientHostShell` (pinned by `MutationGatewayCoverageTests.Only_the_host_shell_drives_its_docker_steps`). |
| `SystemInfoOperations.cs` | Per-server system info/reachability, host CPU/memory usage (Prometheus, /proc exec, or container-stats fallback). |
