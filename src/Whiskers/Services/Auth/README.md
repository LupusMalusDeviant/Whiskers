# Services/Auth

Authorization primitives used across the app: who the current user is, what role they hold, and whether their email is allowed in.

Authentication itself (Google OAuth / OIDC) is wired in [`../../Startup/WhiskersAuthenticationExtensions.cs`](../../Startup/WhiskersAuthenticationExtensions.cs); this folder is the **authorization** layer that sits on top.

## Behaviour notes

- **Whitelist semantics (C5):** enabled **and non-empty** ⇒ only listed emails; enabled **and empty** ⇒ deny all. The first-run seed from `GoogleAuth:AllowedEmails` drops blank entries and trims and de-duplicates the rest; with none left nothing is seeded and the whitelist stays disabled (compose passes an unset `GOOGLE_ADMIN_EMAIL` as an empty entry). Disabled (never configured) ⇒ **fail-open only while the instance is unconfigured** (`IRoleService.HasAnyRoles()` is false); as soon as *any* role exists, a disabled whitelist is **fail-closed** — only users with an explicit role entry are admitted. So the admin bootstrap alone makes a fresh instance fail-closed without the operator touching the whitelist. The Settings UI refuses to save an enabled+empty whitelist so an admin can't lock themselves out. `SaveWhitelistAsync` deep-copies the incoming data so the enforcement snapshot never aliases a caller-owned list. Since R1-11 the Settings page calls `SaveWhitelistAsync` / `SaveRoleDataAsync` only through the Mutation Gateway (`config.whitelist` / `config.roles`, Admin); the service logic is unchanged, and the first-run wizard is the one documented direct caller.
- **Admin bootstrap (C5):** `RoleService.InitializeAsync` seeds an Admin role from `WHISKERS_ADMIN_EMAIL` (provider-neutral) + the first `GoogleAuth:AllowedEmails` entry — **first run only** (neither `roles.json` nor its previous generation `roles.json.bak`, R1-35; a directory in its place is refused, not a first run); an existing file is loaded and never overwritten. To re-seed the admin, delete both files. Fixes the chicken-and-egg where the admin email seeded the whitelist but not the Admin role, leaving the Admin-gated Settings unreachable.
- **Role writes persist first, publish after:** every role writer saves `roles.json` before the new roles take effect, under the shared `AccessControlWriteGate`; a failed save throws and leaves the roles in force unchanged.
- **Role updates are snapshot-isolated:** `RoleService` clones role data before caching/persisting and snapshots under its write-lock before serializing — an unsaved UI edit never mutates the live enforcement list, and a concurrent write can't corrupt serialization (same discipline as the whitelist).
- **Session revocation (R1-26, INV-09):** a local-password cookie carries the account id and its security stamp (`AuthConstants.SecurityStampClaim`); the cookie is re-checked on every request, a circuit every 30 s, a UI mutation on every call, through `ISessionValidator`. Deleting the account, changing its stamp (every R1-49 credential change does), removing the email from the whitelist ends the session; a lowered role holds on the next request and ends a circuit that started higher. Everything that cannot be checked is refused. An open `ContainerHub` connection is re-checked on every call (`Hubs/SessionHubFilter.cs`) and closed when revoked. Every `GetRoleAsync`/`HasRoleAsync`/`CheckSessionAsync` call is a fresh check (no reuse: these roles gate approvals and principals pages hand to stores), and each valid one is reported to the circuit (`NoteRole`), whose 30-s check compares against the highest role any page was handed. Open hub connections are also swept every 15 s (`Hubs/HubSessionSweep.cs`), because the server broadcasts to them.
- **Federated identity binding (R1-27, INV-05):** the IdP subject is the identity, not the address. A federated cookie carries `Federated` as its type and a binding id; `SessionValidator` checks that binding (still present, still the same account) on every request, and refuses any federated session while no explicit Admin exists (`setup_incomplete`) and every cookie of the pre-R1-27 types (`binding_missing`). Local and federated sessions with the same address are checked by different stores and never vouch for each other. Removing an address from roles/whitelist prunes its bindings in the same write; a recycled address therefore needs a new verified sign-in or an Admin confirmation. See [`docs/operations/identity-bindings.md`](../../../../docs/operations/identity-bindings.md).
- **Local credential lifecycle (R1-49):** see [`docs/operations/local-accounts.md`](../../../../docs/operations/local-accounts.md). No temporary passwords: a reset, an invitation and the host recovery issue a one-time code that cannot sign in and only sets a new password at `/account/recover` — the change on first use is enforced by construction. **Local accounts have no MFA in 1.0**; production signs in through the IdP (OIDC) with MFA.
- **Synthetic agent identity:** agent tool execution runs under `AgentSyntheticScheme` carrying the caller's real MCP level in `McpLevelClaim`; tool-internal `McpPermissionCheck` enforces that level rather than granting Admin. This is deliberately **not** the `AuthDisabled` admin scheme.
- **Local login (F1):** ASP.NET Identity provides username/password auth *additively* — `AddIdentityCore<AppUser>` (no competing cookie scheme, no `RoleManager`), a separate `WhiskersIdentityDbContext` (users only) in `Whiskers.Data`, and the `POST /login-local` endpoint (in the pipeline) which validates the password, applies the **same** whitelist gate as Google/OIDC, and issues the **existing** cookie carrying a `ClaimTypes.Email` claim — so roles resolve from `roles.json` exactly as for a federated user. No parallel role system.
