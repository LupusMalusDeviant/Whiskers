# Startup

The composition root, split out of `Program.cs` so it stays a thin orchestrator (RoadToSAP §6 DoD).
`Program.cs` is now ~50 lines: resolve data paths → optional `--migrate-to-postgres` CLI → **apply a pending
F3 self-restore** (`RestoreBootHandler`, the one step that must run *before* anything opens the DB or reads the
DataProtection key ring) → call these extension methods in order → `Build()` → configure the HTTP pipeline →
run startup → `Run()`. Every block was moved **verbatim** — same services, same middleware order; only the
location changed.

| File | Extension methods | What |
|---|---|---|
| `WhiskersHostingExtensions.cs` | `AddWhiskersConfiguration`, `AddWhiskersModules`, `AddWhiskersCoreServices`, `AddWhiskersUi` | UI-writable config layers + data-protection keys; the module pipeline (Core no-op defaults → each enabled module's `ConfigureServices` → MCP tools → nav registry); the remaining Core services (Docker, health, metrics, VPN, database, audit, startup initializers); UI (localization, MudBlazor, Blazor server components, SignalR). R1-31: the data-protection key ring stays in `keys/` with the same application name, its keys encrypted through `VaultKeyRing.AddVaultProtectedKeyRing` (user-approved; the authentication setup is unchanged). R1-54: the explicit Warning list of notification HttpClient log categories includes the channels' shared factory client `notification-channels`. R1-49: `ClientAddressHubFilter` is a global, read-only hub filter (it exposes the calling connection's client address to the call and refuses nothing), and `CircuitClientAddress` a circuit handler keeping it for the circuit — the recovery page's per-client limit; the HTTP pipeline is unchanged. |
| `WhiskersAuthenticationExtensions.cs` | `AddWhiskersAuthentication` | **Security-sensitive — protected layer (docs/ARCHITECTURE.md "Security-critical areas", ADR-0002):** cookie session + optional Google/OIDC providers, the per-request session re-check (`SessionCookieValidation`, fail closed since R1-26), or full LAN bypass. With `Oidc:RequireHttpsMetadata=false` the OIDC nonce and correlation cookies are `SameAsRequest` (Secure over HTTPS, not over plain HTTP; otherwise the framework's `Always`). Isolated so the auth wiring is reviewable in one place. |
| `WhiskersPipelineExtensions.cs` | `ConfigureWhiskersHttpPipeline`, `RunWhiskersStartupAsync` | The HTTP request pipeline in its **fixed, security-critical order** (forwarded headers → path base → exception handler → localization → static files → antiforgery → **setup redirect (W1)** → **maintenance gate (F3)** → authentication → LAN bypass → MCP bearer → authorization → health/culture/auth/hub/MCP/webhook/metrics/self-backup-download endpoints → Razor components; the language cookie of `/set-culture` is HttpOnly, Lax and Secure over HTTPS), then the startup warm-up (`IInitializable` loop in `Order` + metrics-DB init/migration + Identity migration & unattended admin seed). Contract 0010: right after both schemas are migrated (`upgradeGuard.CompleteAsync()`) it runs the guardrail store's second start phase (`GuardrailStore.ReconcileMarkerAsync`), which decides a missing policy by the database's record. R1-31: `RunWhiskersStartupAsync` encrypts plaintext data-protection key files right after the initializers (vault started, key ring not yet read) and plaintext webhook secrets and rollback snapshots right after the database migration; a failure is logged and leaves them as they are. R1-40: `/metrics` also reports the notification outbox (`whiskers_self_notification_outbox_pending`, `whiskers_self_notification_outbox_total` by result: redelivered, exhausted, dropped; `whiskers_self_notification_outbox_unsaved` 1 while a change is not on disk yet). R1-41: every label value in `/metrics` goes through `PrometheusText.Label`, the `# ERROR` comment through `PrometheusText.Comment`. R1-53: `RequestCorrelationMiddleware` is registered **first**, in front of the forwarded headers — it reads only `X-Request-Id` and the current activity and decides nothing, so the chain behind it keeps its order (`OperationalCorrelationTests` pins the order of correlation → forwarded headers → antiforgery → authentication → MCP bearer → authorization); `/metrics` adds the audit trail's completeness (`whiskers_self_audit_events_pending`, `whiskers_self_audit_intents_unsettled`, `whiskers_self_audit_legacy_write_failed`, from `IAuditRecovery.Health`: no database call; the outbox count is a directory listing). |
| `WhiskersLoggingExtensions.cs` | `AddWhiskersLogRedaction` (`AddLogRedaction`) | R1-25 (INV-51): replaces the `ILoggerFactory` registration with a `RedactingLoggerFactory` around it — every `ILogger`/`ILogger<T>` the app resolves writes redacted entries — and keeps the request log of **every** HttpClient (notification channels, AI providers, cloud and registry clients) at Warning by default in code. The real factory stays behind it, so providers, their filter rules (`Logging:Console:LogLevel`, the event log's Warning floor), scopes and disposal are unchanged. `BootSettings.AssertBoot` checks it on every boot test. R1-53: structured console logs need no setting of Whiskers' own — `Logging:Console:FormatterName=json` (+ `FormatterOptions:IncludeScopes=true`) selects the framework's JSON formatter behind the same redaction, scopes included (`OperationalCorrelationTests`; guide: `docs/operations/observability.md`). |
| `SetupRedirectPaths.cs` | — | Path/verb rules for the **W1 setup-redirect** gate, split out so they are unit-testable without a live pipeline: the anonymous-infra allowlist plus `IsHtmlNavigation` (only genuine top-level HTML GETs are funneled to `/setup`, which is load-bearing — `MapStaticAssets` serves *fingerprinted* assets at the root, so no prefix allowlist could catch them). |
| `MaintenancePaths.cs` | — | The same shape for the **F3 maintenance** gate: its own exempt allowlist (a separate list, so the two gates stay independent), reusing `SetupRedirectPaths.IsHtmlNavigation`. |
| `WhiskersMutationGatewayExtensions.cs` | `AddWhiskersMutationGateway` (`AddGuardrailPolicy`, `AddMutationGateway`, `AddMutationScopeGuard`) | The core guardrail policy and approvals (PC-D8: engine, store, rule catalog, tool registry, approval store and gate, direct-MCP guard, principal resolver, `GuardrailStore` warm-up), the Mutation Gateway (ADR-0005) with the per-circuit `IUiMutationRunner` for pages and the `IAutomationMutationRunner` / owner resolver / owner store for unattended runs (`Automation` options section), and the scope guard that wraps every service interface with `[MutatingOperation]` methods. Called **last** in `Program.cs` so module registrations are wrapped too; the original instance sits behind a keyed holder with the same lifetime, so disposal and singleton identity are unchanged. R1-39: also the shutdown drain (`ShutdownDrain` as `IShutdownDrain` and lifecycle service; the host `ShutdownTimeout` is raised to at least 45 s) and the start-up `InterruptedWorkReconciler`. |

**Ordering guarantees preserved:** the module no-op defaults are still registered *before* the module loop
(last-registration wins); the auth middleware chain keeps its exact order; the `IInitializable` warm-ups still
run sorted by `Order`. The block-call order in `Program.cs` differs slightly from the old inline layout, but
that is DI-neutral — there are no cross-block duplicate service types, and the only multi-registration
`IEnumerable`s (`IInitializable`, `IVpnProvider`) are either order-independent or sorted at use.

Verified behaviour-neutral: build + full tests + the `BootMatrixTests` (all-on / only-core / example-on) +
a real Development boot in **both** auth modes (LAN bypass: pages render; real auth: protected pages redirect
to `/login`, `/login` + `/healthz` stay anonymous).
