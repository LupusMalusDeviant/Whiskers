### R1-01 — Refuse unattended confirmation

**Why:** Known item **8** is confirmed. `MutationGateway.cs:159–177` forwards every `Confirm` to the approval gate. `ApprovalGate.cs:113–124` reuses an approved fingerprint on a later identical call. Automation has neither an occurrence identifier nor an unattended-denial branch. The existing automation test only asserts “not executed” on the first occurrence (`AutomationMutationRunnerTests.cs:215–225`).

**Scope:** Gateway, automation runner, approval adapter; approximately 5–7 files.

**Acceptance criteria:**

- [ ] An unattended `Confirm` returns `Denied`, creates no executable approval grant, and invokes no mutation.
- [ ] `AutomationMutationRunnerTests.Approving_a_refused_occurrence_cannot_release_the_next_occurrence` covers two scheduled occurrences and an intervening approval attempt.
- [ ] `KillSwitchTests.Unattended_runs_never_auto_confirm` covers scheduler, AutoUpdate and AutoPatch.

**Out of scope:** Interactive and direct-MCP approve-then-retry behavior; durable approvals.

### R1-02 — Fail-closed, immutable policy configuration

**Why:** INV-25/28; TA-32/33, C-09/15. Invalid or timed-out regexes return `false`, allowing the call (`Services/Guardrails/BuiltInGuardrailRules.cs:165–171`). `GuardrailStore` exposes and saves caller-owned objects (`GuardrailStore.cs:29–30,83`). Its live state is changed before persistence succeeds.

**Scope:** Guardrail rules/store/configuration and tests; approximately 7–10 files.

**Acceptance criteria:**

- [ ] Invalid regex, timeout, unreadable policy and invalid active preset deny execution.
- [ ] Saving or obtaining configuration cannot expose mutable live objects; failed persistence leaves the previous policy active.
- [ ] Invert `GuardrailEngineTests.Invalid_policy_regex_does_not_throw` from Allow to Deny; add `PolicyFailClosedTests` and `PolicyChangeAuditTests.Unsaved_edits_do_not_change_live_policy`.

**Out of scope:** Persisted decisions and policy-change audit storage.

Agent identity is synthesized from display/email/key fields (`Services/Agent/AgentToolInvoker.cs:184–198`); triggers share `McpKeyId="ai-trigger"` (`Triggers/AiTriggerDispatcher.cs:108–110`).

**Scope:** Principal models, principal adapters, persisted identity fields, paired provider migrations; approximately 12–15 files.

**Acceptance criteria:**

- [ ] Stable principal, credential, session and delegation identities survive propagation without parsing display names.
- [ ] `PrincipalPropagationTests` covers Human → Agent → Automation and ApiKey → Agent, including renamed keys and two distinct triggers.
- [ ] Legacy identity migration is explicit and ambiguous identities remain suspended.

**Out of scope:** Federated-login binding and session revocation.

### R1-04 — Preserve automation delegation and revoke deleted owners

Owner resolution checks whitelist/role, not the existence of the local Identity account (`AutomationMutationRunner.cs:87–96`). Authority loss refuses runs but does not fulfill PC-D6’s suspension requirement.

**Scope:** Ownership resolution, task provenance, scheduler execution/takeover, owner settings; approximately 12–15 files.

**Acceptance criteria:**

- [ ] Agent-created tasks retain delegation restrictions and cannot become ordinary human-authorized tasks.
- [ ] `AutomationMutationRunnerTests` covers deleted local Identity rows, demotion, whitelist removal, revoked keys and agent tool/argument/confirmation restrictions.
- [ ] Refused items suspend and notify an Admin; takeover records the old/new authority.
- [ ] Set the documented 1.0 `RequireOwner` default without removing the accepted explicit grace-period behavior.

**Out of scope:** Reconsidering grace-period or AutoPatch takeover decisions.

- [ ] Proxies are disabled for these clients (`UseProxy = false`), since a proxy's address says nothing about the
  destination; a test configures an `IWebProxy` pointing at a local listener and asserts that nothing arrives there.
  An installation that reached Slack or Telegram through an egress proxy loses that path: the CHANGELOG carries an
  upgrade note, and such a delivery fails with a reason of its own (not a generic network error).
- [ ] The upgrade cannot silently cost all alerts: every existing LAN or Tailscale channel (a self-hosted ntfy,
  Mattermost, Matrix, an SMTP relay) is refused from the first start after the upgrade until an Admin adds an
  exception. The CHANGELOG upgrade note names this case; the startup log and the Admin-only notification settings
  page list each configured channel the guard would refuse, with the address that would be refused — tested. The
  startup listing is best-effort: it never delays `/readyz`, and a host that does not resolve is listed as
  "unresolved". The
  listing names scheme, host and port only, never the path or query (Slack and Discord carry their secret in the URL
  path; R1-25 applies to this new sink too). The anonymous `/readyz` stays status-only
  (`Startup/WhiskersPipelineExtensions.cs`), so nothing internal leaks there. A guard refusal is final for that
  delivery: `CompositeNotificationService.SafeSend` does not retry it.
- [ ] Exceptions are narrow: an Admin-only list of entries, each either an IP literal plus port, or a name plus port
  plus the address(es) it may resolve to. The guard compares the **connected address** with the entry, so an excepted
  name that rebinds to another address (for example `169.254.169.254`) is refused — tested. Ranges or wildcards are
  not accepted. Each change is a gated configuration write (R1-11) with audit (R1-22); Viewer/Operator and a demoted
  Admin are refused, the kill switch refuses, an audit failure refuses before the list is published, and a failed
  save leaves the live list unchanged.
- [ ] Removing or narrowing an exception also ends the connections it allowed: the guard runs in `ConnectCallback`,
  which a pooled keep-alive connection does not pass again, so a published change replaces the outbound handler
  (or its connection pool) before the next delivery starts. A test removes an exception and sends a second request
  that would otherwise reuse the keep-alive connection; it is refused.
- [ ] A refused delivery is a visible notification failure (R1-40), with the reason and without the URL's secrets
  (R1-25).

**Out of scope:** Inbound webhooks (R1-09/10). The other operator-configured outbound fetchers — those the audit lists
in `docs/v1/audit/E-exec-injection.md` (registries, image search, DNS, the VPN login server) plus the Prometheus
endpoint, the cloud provider APIs, Ollama/AI provider endpoints, git-deploy remotes
(`Services/GitDeploy/GitDeployService.cs`) and the Kubernetes API server — and the certificate monitor's raw TCP probe
(`Services/Certificates/CertificateProbe.cs`): they address infrastructure an Admin configures on purpose, often on
the LAN; moving them onto the guard is a follow-up package, not part of this one.

### R1-55 — Tiered metric retention with averages and peaks

**Why:** Server and container metrics are stored raw every collection interval and deleted after one hard retention
window (`Services/Metrics/MetricsCollectorService.cs:265–275`); thinning happens only at query time
(`Services/Metrics/MetricsQueryService.cs` `Downsample`). Long ranges cost storage and query time, and a short spike
averaged away in a query is gone. Beszel keeps 1-minute records briefly and rolls them up into coarser tiers that
store the average **and** the peak of each window (`internal/records/records.go`, `records_deletion.go`).

**Scope:** Roll-up job, tier tables or a tier column (paired SQLite/PostgreSQL migration, additive), query selection by
range, a result model carrying average **and** maximum per point (replacing the averaging in
`MetricsQueryService.Downsample`; the monitoring MCP tools in `Mcp/Tools/MonitoringTools.cs` already print avg/max, but their
maximum must come from true maxima, not from averaged points, and their period list — today `1h/6h/24h/7d` — gains
`30d`; so do the UI period selectors in `Components/Pages/Dashboard.razor` and `Components/Pages/ContainerDetail.razor`),
retention
settings, SQLite → PostgreSQL migrator (R1-34's transactional transfer); approximately 12–16 files.

**Acceptance criteria:**

- [ ] `MetricRollupTests`: raw samples roll up into fixed tiers (for example 10 min / 1 h / 8 h) keeping average,
  maximum and sample count per series. Only closed windows are rolled up; a roll-up interrupted by a restart neither
  loses nor double-counts a window (idempotent per window), and retention never deletes data of any tier (raw or
  rolled up) before every successor window built from it is durably committed — also when a higher-tier roll-up
  fails while retention runs, and across a restart (tested for raw → first tier and first → second tier).
- [ ] A query covers its whole range without gaps or duplicate timestamps: coarse tiers for the old part, finer tiers
  and raw data for the recent part (stitched at window boundaries). Averages that combine windows are weighted by
  sample count; maxima are the true maxima of the original samples. Tests cover uneven sample counts, empty and
  partial windows, tier boundaries and the newest raw tail. Thinning a long range to the chart's point budget keeps
  each point's maximum (no averaging of maxima away): a chart and an MCP query over 30 days show the true peak of a
  2-minute spike and the last minutes of data.
- [ ] Each tier has its own retention; raw retention can shrink without losing the long view. `AlertHistory`, today
  pruned with the same `RetentionDays` (`MetricsCollectorService.cs:275`), keeps a retention of its own and is not
  shortened by a smaller raw retention. Defaults documented.
- [ ] Retention is configuration-only today (`Configuration/MetricsSettings.cs`, nothing writes it): this package
  creates the settings-store write path and its UI, and a value from the environment or `appsettings` stays read-only
  and is shown as such, so R1-11's coverage test has one write path to enumerate.
- [ ] Retention settings are gated configuration writes (R1-11) with audit (R1-22): Viewer/Operator and a demoted Admin
  are refused, the kill switch refuses, an audit failure refuses before the setting is published, and a failed save
  leaves the live settings unchanged. Every new query and results path enforces the existing read role.
- [ ] The prune block in `MetricsCollectorService` is also touched by R1-23 (audit retention): whichever lands second
  rebases onto the other; the package notes the order it was built on.
- [ ] Additive paired migrations; existing raw data stays readable and is rolled up once on upgrade; the
  `--migrate-to-postgres` path copies the tiers.

**Out of scope:** Whiskers' own self-metrics (`SelfMetricSamples`, pruned by `SelfMetricsRecorder`), which keep their
retention. Managing the storage of an external time-series database (VictoriaMetrics). Readings Whiskers
persists in its own tables are in scope whatever their source — including host readings fetched from Prometheus/
node_exporter (`MetricsSourceDispatcher.cs:48–50`, stored by `MetricsCollectorService.cs:173–191`).

### R1-56 — Sustained-breach conditions and quiet hours for alerts

**Why:** Sustained conditions exist but are inconsistent: container CPU/RAM and host disk alerts count consecutive
samples (`Services/Metrics/MetricsCollectorService.cs:301–317`, `:370–377`; `MetricAlertSettings.SustainedMinutes`,
converted assuming a 30-second interval), while host-load alerts use elapsed time with hysteresis
(`Services/Metrics/HostLoad/BreachTracker.cs`, which keeps the breach start while a reading sits inside the hysteresis
band and ends it only after the value stayed below the clear line for `ClearedFor`, 5 minutes in
`HostLoadEvaluator.cs`). A changed interval or missing samples silently change what "3 minutes" means. No alert can be held back during
a planned window. Beszel alerts on a value averaged over N minutes and supports quiet hours
(`internal/alerts/alerts_system.go`).

**Scope:** One duration model for threshold alerts — `BreachTracker` generalised, not a new model — with an injected
clock in the collector (`MetricsCollectorService.cs` reads `DateTime.UtcNow` today), quiet hours, durable suppression
state (paired SQLite/PostgreSQL migration, additive), a named set of never-suppressed events, a structured CVE severity
on the CVE event, settings UI with en/de strings; approximately 14–18 files.

**Acceptance criteria:**

- [ ] `SustainedAlertTests` pin one documented semantics for every threshold alert: duration is elapsed time, not a
  sample count. A reading at or above the threshold starts or continues a breach; a reading inside the hysteresis
  band neither resets nor clears it; a breach ends only after readings stayed below the clear bound (threshold minus
  the documented margin) for the documented clear duration, with a Cleared finding if the breach was reported —
  as `BreachTracker` does today, so the flapping its class comment describes (`Services/Metrics/HostLoad/
  BreachTracker.cs`) does not return (tested). A
  gap longer than the documented tolerance resets the breach rather than bridging it, and is never silent: a gap
  raises a visible `metrics_gap` finding for the series (a host whose node_exporter is down, a container whose stats
  call fails — `MetricsCollectorService.cs:150–153` only logs a warning today), since `server_unreachable` comes from
  the health monitor and does not cover these cases. A test shows what the operator sees. A changed collection
  interval does not change the effective duration. Deterministic tests (fake clock) cover each rule, and the existing container/disk/host-load
  alerts are migrated to it. Today `high_cpu`, `high_memory` and `high_disk` re-fire after `CooldownMinutes`
  (`MetricsCollectorService.cs`, Settings panel): the package states what replaces that — one raise per breach plus
  a Cleared finding, with `CooldownMinutes` kept as the minimum gap between two breaches of the same series — updates
  the Settings panel, and carries the change in the CHANGELOG. Raised and Cleared are state transitions: like
  reachability and certificate events today (`NotificationThrottler.IsTransition`) they bypass the per-channel
  throttle; a test delivers two breaches and their recoveries inside one channel-throttle window. `metric_anomaly` (the rolling z-score rule in
  `MetricsCollectorService`) is a point-in-time outlier, not a threshold breach: it keeps re-firing after
  `CooldownMinutes` as today and is not migrated to breach semantics.
- [ ] Quiet hours (per rule or global, IANA time zone explicit) suppress delivery to channels, never evaluation: the
  in-app feed and `AlertHistory` keep recording during quiet hours, and AI-trigger dispatch is not held (a trigger
  decides for itself). Windows crossing midnight, DST changes and an invalid time zone (refused on save) are tested.
- [ ] Event types come from one registry, created by this package (today the literals are spread across the
  producers): `NotificationEventTypes`, constants plus the two runtime patterns
  `log_alert:<severity>` and `<kind>_recovered`, that `NotificationFormatter.Describe`, `NotificationsLog.razor` and the
  suppression rule all read; an architecture test refuses any `EventType` value not drawn from it (variables included,
  `ServerCircuitBreaker`, `WebhookService`, `MetricsCollectorService.Emit`). A type the rule does not know at runtime
  is delivered, never suppressed.
- [ ] Never suppressed by quiet hours: a named constant set in that registry (for example `UnsuppressibleEvents`)
  containing the administrative events (`automation_suspended`, `automation_refused`, INV-04)
  and `cve_finding` notifications whose batch contains a Critical finding. `NotificationEvent` has no severity today
  (`CveMonitorService` sends one aggregate event per target with severities only in its text): the aggregate gains a
  structured field with the highest CVE severity in the batch, the rule reads that field, and one Critical finding
  makes the whole batch unsuppressible. The set also holds `webhook_disabled` (R1-09's admin notice, INV-04),
  `agent_approval` (approval requests expire under R1-15, so holding one would silently kill it), `loops_paused_reminder`,
  `log_scan_suspended`, `monitoring_stalled` (`Services/Observability/ScanSupervisor.cs`: nothing is being checked, so
  holding it hides the gap) and `auto_update_failed` (`Services/AutoUpdate/AutoUpdateService.cs`,
  `Services/AutoPatch/AutoPatchService.cs`: a failed update can leave a container down). A test delivers each member during quiet
  hours, and a classification test requires every
  registry entry to be assigned to suppressible or never-suppressed, so a new event type cannot land unclassified.
  The set bypasses quiet hours only: the per-container mute keeps its meaning (only `AdministrativeEvents` override
  it, as today, INV-04); a Critical CVE batch for a muted container stays muted. Events
  for audit failures or the kill switch do not exist today; adding them is not part of this package.
- [ ] What was suppressed is recorded durably (bounded aggregation per rule and target; past the bound the summary
  carries an "N further events suppressed" count, so overflow is never silent) and delivered as one summary
  after the window, through R1-40's outbox — widened by this package from Critical notifications to these summaries —
  with an idempotency key: the summary is created exactly once (a restart during quiet hours neither loses nor
  doubles it) and delivered at least once — a crash after a provider accepted it but before Whiskers recorded that
  may deliver it again, which the documentation states (Slack and others offer no receiver-side deduplication);
  tested at that crash boundary. A window that ends early (rule changed) delivers it then. The
  summary bypasses the per-channel `NotificationThrottler`, as state transitions do (tested).
- [ ] Rule and quiet-hour changes are gated configuration writes (R1-11) with audit (R1-22): Viewer/Operator and a
  demoted Admin are refused, the kill switch refuses, an audit failure refuses before publication, and a failed save
  leaves the live rules unchanged.

**Out of scope:** On-call rotation and escalation chains.

### R1-57 — Endpoint checks from the managed host

**Why:** Whiskers watches certificates (`Services/Certificates/`) and the hosts themselves, but cannot check whether a
service a host exposes answers — from that host's side of the network. Beszel's agent runs ping/HTTP/certificate
checks locally (`agent/network_monitor_*.go`). Whiskers has no read-only **command** channel to a host (Prometheus/
node_exporter is a read-only metrics channel, not a command channel): host commands run through
`HostCommandExecutor` (`Services/Server/HostCommandExecutor.cs:51–64` — local `nsenter`, a one-shot privileged
container over the mTLS Docker connection, or SSH), so each check run is a privileged execution and is treated as
one.

**Scope:** Check definitions (HTTP status/latency, TCP connect, TLS expiry), fixed check commands run through the
existing executor as a gateway capability on the host the check is bound to, check results (paired SQLite/PostgreSQL
migration, additive) as metrics with R1-56 alerting; approximately 12–16 files. The transport itself (protected area)
is not changed; it hands a command string to a POSIX shell (`sh -c` locally and over mTLS, the remote login shell over
SSH), so operands are quoted into a fixed template rather than passed as argv. Every check runs on a managed host —
the Local server included — through that executor; Whiskers itself opens no connection to the target.

**Acceptance criteria:**

- [ ] `EndpointCheckTests` cover HTTP, TCP and TLS-expiry checks with timeouts and a bounded result size. The bound
  comes from the templates themselves (`curl -o /dev/null -w …`, output cut with `head -c`), since the mTLS transport
  applies no output cap (`HostCommandExecutor.cs:59–61`); a test sends a large response through the TCP transport.
- [ ] A check run is a registered gateway capability with an owner principal (INV-04): the owner's authority is
  re-checked on every run, the kill switch and an audit failure refuse the run, and every run is one audited gateway
  event with its own operation id (R1-18). Runs come from one background loop under R1-41's rules, and a check's
  interval has a validated minimum of 60 seconds, which bounds runs and their audit rows (at most 1440 per check and
  day; audit retention is R1-23's). Executor calls per run are bounded separately: one `getent`, then at most 4
  allowed addresses tried, each attempt under the check's timeout and the whole run under one deadline; tests cover
  a name with many answers and every address failing.
- [ ] **Prerequisite — executor deadlines.** Today the mTLS path drops cancellation (`HostCommandExecutor.cs:61`) and
  `HostShellOperations.cs:56` inspects or pulls the helper image, creates and starts the container before its timeout
  starts, with log retrieval and cleanup outside it; a stalled Docker step can outlive any check deadline. Before
  checks ship, the executor honours one deadline across setup, execution, result retrieval and cleanup on every
  transport. This touches the mTLS layer, a protected area: it needs the maintainer's explicit approval and lands as
  its own reviewed change (or inside R1-57 once approved). Tests cover a stalled image pull/create, a stalled command
  and a stalled log retrieval, each ending within the deadline.
- [ ] The URL scheme is `http` or `https` only, enforced on save and in the template (`curl --proto '=http,https'`);
  a test refuses `file:`, `gopher:`, `dict:` and `ftp:` URLs before anything runs.
- [ ] The commands on the host are fixed templates. Target, port and path are validated against strict allow-lists
  (R1-42 validators, INV-41) and inserted single-quoted; a test proves that an option-leading operand (`-…`) or one
  containing shell metacharacters, quotes or whitespace is refused **before** anything runs. No new agent, no new
  listening port.
- [ ] A check runs in three steps so the host's DNS view is kept and the range decision stays in Whiskers: (1) a
  fixed resolve command on the host (`getent ahosts '<name>'`); (2) Whiskers checks every answered address against the
  R1-54 default-denied ranges and the check's exceptions; (3) a second fixed command pinned to the chosen address —
  HTTP: `curl -q -s -S --max-time <timeout> --resolve '<name>:<port>:<ip>' --noproxy '*'` (`-q` first, so no
  `.curlrc` changes the check; no `-L`, so a redirect is not followed and a 3xx counts as the check's answer, judged
  against its expected status);
  TLS expiry: `openssl s_client -connect '<ip>:<port>' -servername '<name>' </dev/null`, bounded by the executor's
  timeout,
  which ends the process (locally) or the one-shot container (mTLS) on expiry; TCP: `nc -z -w <timeout>
  '<ip>' '<port>'`. The TLS expiry is read with `… | openssl x509 -noout -enddate` and requires a `notAfter=` line;
  the check parses `notAfter` only — chain and hostname verification are out of scope for it.
  Every template sends stderr into the bounded stream (`2>&1` before the cut) or discards it, and carries the tool's
  exit status inside the bounded stream (`( cmd 2>&1; echo "__rc=$?" ) | head -c N`), since a POSIX `sh` has no
  `pipefail`; a missing or non-zero marker is a failed check. Each parser also requires positive evidence (a parsed
  3-digit HTTP status, a parsed `notAfter`, the TCP marker 0) — tested with curl exit 28/6/7 and an openssl connect
  failure. The TLS template keeps both statuses: `s_client`'s output is captured on its own with its marker
  (`( openssl s_client … 2>&1; echo "__rc=$?" ) | head -c N`) and the certificate is parsed from that bounded output
  in Whiskers (or with `openssl x509` fed from it in a second step whose own marker is checked); a non-zero `s_client`
  status fails the check even when a certificate was printed — tested with certificate output followed by exit 1. The
  pinned port is the URL's effective port (80/443 when the URL names none); a definition port that disagrees with the
  URL is refused on save, since curl would otherwise fall back to the host's DNS — tested with and without an explicit
  port. When the name answers several addresses, every answer must pass (one denied answer refuses the check, as in
  R1-54), and the complete answer is validated before any address is chosen — a truncated or unparsable resolve output
  refuses the check; step (3) then tries at most the first 4 unique allowed addresses in answer order (`getent ahosts`
  repeats an address per socket type) until one answers, and the result records which address answered, that none
  did, and how many further addresses were not tried. Tests: a denied fifth answer refuses the check; five allowed
  answers try four. An IP-literal
  target skips
  step (1) and must be a canonical dotted quad or RFC 5952 IPv6 literal; decimal, octal and hex forms are refused. IPv6 addresses are bracketed where
  the tool needs it (`'<name>:<port>:[<ip>]'`, `'[<ip>]:<port>'`) — tested with an IPv6 answer. Tests cover a redirect
  to `169.254.169.254`, a name answering an internal address, IPv4-
  mapped IPv6 forms and a refused destination. Internal targets — the usual case for a LAN service — need an explicit,
  Admin-only exception per check (IP literal or name plus allowed addresses, as in R1-54).
- [ ] The required tool set per host is documented: `getent`, `curl`, `openssl` and one `nc` flavour (OpenBSD
  netcat, the Debian/Ubuntu default) for the TCP check; another `nc` variant is reported as unsupported rather than
  guessed at.
- [ ] A missing tool on the host (`getent`, `curl`, `openssl`, `nc`), a non-zero exit or unparsable output is a failed
  check, never a pass — tested.
- [ ] A check definition is a gated configuration write (R1-11) with audit (R1-22): Viewer/Operator and a demoted
  Admin are refused, the kill switch refuses, an audit failure refuses before publication. A check bound to a server
  without a shell transport (a Kubernetes server without SSH host; `HostCommandExecutor` returns exit code -1 there)
  is refused on save, tested.
- [ ] Results feed the alert pipeline with R1-56's duration semantics.

**Out of scope:** Synthetic browser checks; checks from outside the fleet or from Whiskers' own process; changing the
host transport; the existing certificate monitor (`Services/Certificates/`), which keeps its own probe.

### R1-58 — Optional disk-health readings

**Why:** Beszel reads SMART, RAID/ZFS state and GPUs on each host (`agent/smart*.go`, `agent/zfs/`, `agent/gpu_*.go`).
Whiskers has none of the disk-health readings. Pending **security** updates are already found
(`Services/Cve/OsCveScanner.cs:40–101`, apt security pocket); a broader update inventory is not part of this package.

**Scope:** Optional read-only sources through the existing telemetry stack (node_exporter textfile collector or
smartctl_exporter), parsers and a host-detail panel; approximately 8–12 files. **Post-1.0:** schedule after the
P0/P1 packages; not a release blocker. The textfile collector needs a host-side job (for example a cron writing
smartctl output); that setup is the operator's, documented in the package, and never a Whiskers write path.

**Acceptance criteria:**

- [ ] `DiskHealthReadingTests` parse SMART/RAID/ZFS states from recorded Prometheus `/api/v1/query` responses
  (fixtures; Whiskers reads the configured `MetricsEndpoint`, never exporter text) into distinct
  states: Healthy, Degraded/Failing, Unknown and Unsupported. Unsupported means a host never had a reading (for
  example a Docker-source server without `MetricsEndpoint`); Unknown means a host had one and it is now missing,
  malformed, partial or stale (older than a documented freshness limit). Freshness is judged by collection-age
  evidence — the collector's last-success timestamp or `node_textfile_mtime_seconds` — never by the query's sample
  timestamp, which a scrape of a stale textfile keeps fresh; a fixture with fresh sample timestamps but an expired
  source file must read Unknown. Neither is ever Healthy, and neither can clear an existing Degraded/Failing state.
- [ ] Disabled by default; enabling is a gated configuration write (R1-11) with audit (R1-22) — Viewer/Operator and a
  demoted Admin refused, kill switch and audit failure refuse, a failed save leaves the setting unchanged — and needs
  no new privileged agent and no write path on the host. The panel enforces the existing read role.
- [ ] A failing disk, a degraded array and a reading that turns Unknown raise alerts through the pipeline (R1-56).
  Unknown alerts only on a transition out of Healthy or Degraded/Failing; Unsupported never alerts — both tested.

**Out of scope:** Running smartctl or package managers through Whiskers' own command channel; a general package-update
inventory beyond the existing security-update findings; GPU readings.

### Learnings from Beszel — deliberately not taken over

- **PocketBase and statistics stored as one JSON field:** Whiskers keeps typed EF Core entities with paired migrations
  (ADR-0004).
- **SSH as a metrics channel:** contradicts the move away from standing SSH keys to Tailscale + socket-proxy/mTLS (`docs/ARCHITECTURE.md`, `docs/ssh-haertung.md`).
- **An own agent with access to the Docker socket:** a second attack surface beside docker-socket-proxy and mTLS
  (protected area); `:ro` on the socket protects nothing.
- **Agent self-update:** would bypass the Mutation Gateway and signature checks.
- **Non-expiring universal enrollment tokens.**
- **Post-1.0 idea, not a package:** an optional light agent that dials out to Whiskers (token + machine fingerprint +
  hub-signed challenge, no inbound port) for hosts without the Tailscale mesh. It needs its own ADR and the protected-
  area approval first.
