### R1-01 — Refuse unattended confirmation

**Why:** Known item **8** is confirmed. `MutationGateway.cs:159–177` forwards every `Confirm` to the approval gate. `ApprovalGate.cs:113–124` reuses an approved fingerprint on a later identical call. Automation has neither an occurrence identifier nor an unattended-denial branch. The existing automation test only asserts “not executed” on the first occurrence (`AutomationMutationRunnerTests.cs:215–225`).

**Scope:** Gateway, automation runner, approval adapter; approximately 5–7 files.

**Acceptance criteria:**

- [ ] An unattended `Confirm` returns `Denied`, creates no executable approval grant, and invokes no mutation.
- [ ] `AutomationMutationRunnerTests.Approving_a_refused_occurrence_cannot_release_the_next_occurrence` covers two scheduled occurrences and an intervening approval attempt.
- [ ] `KillSwitchTests.Unattended_runs_never_auto_confirm` covers scheduler, AutoUpdate and AutoPatch.

**Out of scope:** Interactive and direct-MCP approve-then-retry behavior; durable approvals.

### R1-02 — Fail-closed, immutable policy configuration

**Why:** INV-25/28; TA-32/33, C-09/15. **Scope:** Guardrail rules/store/configuration and tests; approximately 7–10 files.

**Acceptance criteria:**

**Out of scope:** Persisted decisions and policy-change audit storage.

> INV-45 ✅ (WP5 path matrix): `AuditPathMatrixTests` reads every row of `PRODUCT_CONTRACT.md` §7 and requires a
> test that drives it against a real `AuditLog` for each outcome it can have (one complete event per attempt, every
> field checked: decision id exactly when the policy step was reached, resolved target, redacted arguments), or an
> exemption pinned by named test methods; the outcomes a row must prove are derived from §7. Paths that refused
> themselves before the gateway wrote no event — AutoPatch nights without an owner, AutoUpdate with a blocked owner
> entry, endpoint-check runs the monitor refused, webhook deliveries that ended before their decision (also with the
> webhook gone, or given up after the start), scheduled tasks refused before the gateway (no target or command, a
> missing or unreadable database container, a protected stopped container, an unknown type) — and now record the
> gateway's Denied event. User decision 2026-11-07: an attempt begins when the handler requests the capability from
> the gateway; a page returning before that (validation, a cancelled confirmation, not found) changes nothing and is no
> attempt — backed by a static check that no page writes state itself and by the scope-guard tests. The fail-closed
> exits for a missing service cannot occur: the boot matrix resolves every service of the boundary. A call cancelled
> after it asked the gateway and before its intent is one Denied event (also at a webhook run's deadline during target
> resolution); an accepted webhook delivery its worker gives up is recorded once, then settled failed and final
> (claim-fenced, retried with back-off); what a stop or crash leaves unsettled is recorded and settled at the next
> start — the acceptance is persisted before the answer, a row an earlier process accepted is never taken over (a
> repeat is busy until it is settled), and a reconciliation pass that cannot settle every row is retried until one
> completes. The "did not run" event is keyed by the run id (one row whichever path writes it, the outbox included),
> and a give-up cut off by a stop keeps its claim, so it is never taken over. The worker's own refusals have a key
> kind of their own and are reconciled as refused; only a refusal honours an event key.

### R1-58 — Optional disk-health readings

**Why:** Beszel reads SMART, RAID/ZFS state and GPUs on each host (`agent/smart*.go`, `agent/zfs/`, `agent/gpu_*.go`).
Whiskers has none of the disk-health readings. Pending **security** updates are already found
(`Services/Cve/OsCveScanner.cs:40–101`, apt security pocket); a broader update inventory is not part of this package.

**Scope:** Optional read-only sources through the existing telemetry stack (node_exporter textfile collector or
smartctl_exporter), parsers and a host-detail panel; approximately 8–12 files. **Part of 1.0** (maintainer decision of
5 November 2026; it was planned post-1.0). The textfile collector needs a host-side job (for example a cron writing
smartctl output); that setup is the operator's, documented in the package, and never a Whiskers write path.

**Acceptance criteria:**

- [x] `DiskHealthReadingTests` parse SMART/RAID/ZFS states from recorded Prometheus `/api/v1/query` responses
  (fixtures; Whiskers reads the configured `MetricsEndpoint`, never exporter text) into distinct
  states: Healthy, Degraded/Failing, Unknown and Unsupported. Unsupported means a host never had a reading (for
  example a Docker-source server without `MetricsEndpoint`); Unknown means a host had one and it is now missing,
  malformed, partial or stale (older than a documented freshness limit). Freshness is judged by collection-age
  evidence — the collector's last-success timestamp or `node_textfile_mtime_seconds` — never by the query's sample
  timestamp, which a scrape of a stale textfile keeps fresh; a fixture with fresh sample timestamps but an expired
  source file must read Unknown. Neither is ever Healthy, and neither can clear an existing Degraded/Failing state.
- [x] Disabled by default; enabling is a gated configuration write (R1-11) with audit (R1-22) — Viewer/Operator and a
  demoted Admin refused, kill switch and audit failure refuse, a failed save leaves the setting unchanged — and needs
  no new privileged agent and no write path on the host. The panel enforces the existing read role.
- [x] A failing disk, a degraded array and a reading that turns Unknown raise alerts through the pipeline (R1-56).
  Unknown alerts only on a transition out of Healthy or Degraded/Failing; Unsupported never alerts — both tested.

> Implemented (2026-11-05; contract [0005](../contracts/0005-disk-health-readings.md), accepted the same day with its
> five decisions as recommended):
> - **Source and query (decision 1):** SMART through node_exporter's textfile collector in `smartmon.sh`'s metric
>   format; md and ZFS from the built-in collectors. `smartctl_exporter` is not supported in 1.0. Whiskers reads only
>   `MetricsEndpoint` through the new typed, cancellable `IPrometheusQueryClient` (`Services/Metrics/PrometheusQueryClient.cs`;
>   `PrometheusMetricsSource` unchanged): six fixed instant queries per host on `server="<id>"`, side by side, 10 s each.
>   Only `"status": "success"` with a `vector` result counts; an error status, another result type or a misshapen field
>   is a failed query, never an empty one.
> - **States (`Services/Metrics/DiskHealth/DiskHealthParser.cs`, pure):** freshness only from `smartmon_smartctl_run` and
>   `node_textfile_mtime_seconds` of `smartmon.prom`, both within 2 hours (decision 2); md and ZFS from
>   `node_scrape_collector_success` = 1 at query time. A value read bad is Degraded/Failing even with old evidence; anything
>   not clearly good with fresh evidence is Unknown (also SMART not available or not enabled on a disk, an inactive md
>   array); an item of the last reading that is gone is carried as Unknown; a failed source query adds a `(query failed)`
>   line, so a host with a failed query never reads Healthy. No items: Unsupported before any reading, Unknown after one.
>   Label values are display-escaped. The last readings are kept in `disk-health.json` (local to the install), so a missing
>   disk stays Unknown across a restart; switching the feature off and on forgets them.
> - **Setting:** section `DiskHealth` `{ "Enabled": false }`, `IDiskHealthSettingsService.SaveAsync` as `config.save` through
>   `IUiMutationRunner` (Settings → *Disk health (SMART, RAID, ZFS)*, `DiskHealthPanel`, Admin only, links the guide).
> - **Monitor:** `DiskHealthMonitor : FleetBackgroundService`, every 5 minutes while on; a server without
>   `MetricsEndpoint` is Unsupported and never queried; failures isolated per host and cycle (R1-41). Off: nothing is
>   queried or shown, open alerts are closed unconfirmed; a removed server likewise.
> - **Alerts (decision 4):** `disk_failing`, `array_degraded`, `disk_health_unknown` — recoverable, never suppressed by quiet
>   hours (nor their `_recovered`) — on `BreachTracker` as 1/0 against 1: raised after 10 minutes, cleared after 10 minutes
>   of good readings, no gap reset. A group neither clearly bad nor clearly good feeds nothing but holds the tracker
>   (`BreachTracker.Hold`: a pending raise or clear starts again), so Unknown and Unsupported never clear an open alert;
>   `disk_health_unknown` is armed per disk, array and pool, only by that item's transition out of Healthy or
>   Degraded/Failing.
> - **UI (decision 5):** the *Disks* block (`DiskHealthBlock`) in each server's expanded dashboard panel, read-only for every
>   signed-in role, hidden while off. **node_exporter (decision 3):** the deploy compose and the onboarding template add
>   `--collector.textfile.directory=/host/var/lib/node_exporter/textfile_collector` (existing read-only `/:/host` mount).
>   Operator guide with the shell script and systemd timer: `docs/operations/disk-health.md`.
> - **Tests:** `DiskHealthReadingTests` (recorded fixtures incl. fresh sample time with an expired run or mtime → Unknown,
>   and the query client over a stub handler), `DiskHealthAlertTests`, `DiskHealthMonitorTests`, `DiskHealthSettingTests`,
>   `ComponentTests/DiskHealthPanelTests`, `OnboardingCommandsTests`; `UiMutationGatewayCoverageTests` lists the new write
>   and handler. **Needs the maintainer / hardware:** a host with real SMART disks and the timer, an md array and a ZFS
>   pool if present in the fleet, and a look at the dashboard block.
> - **Review round 1 (2026-11-05):** the query client fails closed on every exception but the caller's cancellation (a
>   cut-off body, `HttpIOException`, an out-of-range sample time); a read that throws is an all-failed reading, so a
>   Healthy host turns Unknown; the block shows the reading's age and treats one older than two cycles as Unknown; a first
>   read with failed queries says "not read yet". `disk_health_unknown` is armed per item (`DiskHealthLostItem`, `Lost` in
>   `disk-health.json`); a null signal holds the tracker (`BreachTracker.Hold`), so good → Unknown → good does not clear
>   at once. Switching off forgets immediately (`IDiskHealthSettingsService.Changed`); renamed devices stay Unknown
>   until then. Every collector sample must be 1; disagreeing duplicates are Unknown; SMART fails only with available and
>   enabled = 1. Per-finding send, per-host read time, `TimeoutStartSec` in the guide, env-set value read-only in
>   Settings. **Follow-up (needs a contract change):** a per-server "forget missing items" action.
> - **Review round 2 (2026-11-05):** items of one kind and name (e.g. `/dev/sda` with two `type` labels) collapse into
>   one line — failing if a copy fails, Unknown otherwise — and the alerts key previous items through a set, so a
>   duplicate (also from an older `disk-health.json`) no longer throws and stops a host's alerting. A switch-off sets a
>   "forget pending" flag that the next holder of the gate honours, also when it is on again by then; `SuppressFlow` is
>   guarded by `IsFlowSuppressed`. The guide documents the per-host reset (disable the server for one cycle), the
>   environment case and the brief stale-Unknown in a large, slow fleet.

**Out of scope:** Running smartctl or package managers through Whiskers' own command channel; a general package-update
inventory beyond the existing security-update findings; GPU readings.

### Learnings from Beszel — deliberately not taken over

- **PocketBase and statistics stored as one JSON field:** Whiskers keeps typed EF Core entities with paired migrations
  (ADR-0004).
- **SSH as a metrics channel:** contradicts the move away from standing SSH keys to Tailscale + socket-proxy/mTLS (`docs/ARCHITECTURE.md`, `docs/ssh-haertung.md`).
- **An own agent with access to the Docker socket:** a second attack surface beside docker-socket-proxy and mTLS
  (protected area); `:ro` on the socket protects nothing.
- **Agent self-update:** would bypass the Mutation Gateway and signature checks.
- **Non-expiring universal enrollment tokens.**
- **Post-1.0 idea, not a package:** an optional light agent that dials out to Whiskers (token + machine fingerprint +
  hub-signed challenge, no inbound port) for hosts without the Tailscale mesh. It needs its own ADR and the protected-
  area approval first.
