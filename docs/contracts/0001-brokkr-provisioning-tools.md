# Contract 0001 — Provisioning tools for Brokkr

Status: **Accepted** · 2 November 2026. Open points 1–3 accepted as proposed; one amendment accepted the same day:
the token tool gets its own capability `gitdeploy.set_token` (the catalog binds exactly one MCP tool to a capability).
Second amendment, accepted 2 November 2026 (review of BK-1): the owner of the app and of the webhook is the person who
approved the call, not the key — see Rules.
Counterpart: Brokkr contract `0006-agentenbetrieb.md`, section 6 (decision D10: Brokkr talks to Whiskers over MCP,
not over a new REST surface).

## Purpose

`brokkr deploy setup` sets up a project's Git deployment in Whiskers in one go: app, repository read token and the
GitHub webhook. Today this is only possible through the UI. This contract adds the missing MCP tools on the existing
`/mcp` endpoint. It adds **no new authentication surface**; the auth middleware stays untouched.

## Boundaries (fixed)

- Transport: JSON-RPC over HTTP at `/mcp`, Bearer API key, as every other MCP tool.
- Every write runs through the Mutation Gateway: policy, approval, audit, operation journal, read-back. No bypass.
  The existing capabilities `gitdeploy.save`, `webhook.save` and `webhook.rotate_secret` get their MCP tool; one new
  capability, `gitdeploy.set_token` (admin, root-equivalent like `gitdeploy.save`), carries the token tool, because the
  catalog binds exactly one MCP tool to a capability.
- The tools are `admin` level (as the capabilities already are). A Brokkr key is an ordinary MCP key at level
  `admin` whose `AllowedTools` list exactly the tools below plus `list_git_deploy_apps`.
- Secrets: the repository token goes in only (never returned, never logged, never in the call log or audit details).
  The webhook secret comes out only in the answer of `create_git_deploy_webhook` and
  `rotate_git_deploy_webhook_secret`; it is withheld from the MCP call log, the audit row and every log line.
- Approvals: a direct MCP call cannot approve itself (PC-D4). When policy requires an approval the tool answers
  `pending approval` with an operation id; a person approves in Whiskers, Brokkr repeats the call with the same
  operation id. Never auto-confirmed.
  *Clarification (review of BK-1, 2 Nov 2026):* the answer is the error envelope
  `{"error":"pending_approval","message":…,"operationId":…,"approvalId":…}`. The repeat is the identical call (same
  tool, same arguments, same key); Whiskers binds it to that open operation (R1-18), so it runs under the returned
  operation id — no extra parameter.

## Tools

| Tool | Capability | Input | Output |
|---|---|---|---|
| `create_git_deploy_app` | `gitdeploy.save` | `name`, `repoUrl` (HTTPS only), `branch`, `composePath`, `serverId`, optional `token` | `id`, `revision`, the stored fields, `credentials: stored/none` |
| `set_git_deploy_token` | `gitdeploy.set_token` (new) | `appId`, `revision`, `token` (empty string removes it) | `revision`, `credentials: stored/none` |
| `get_git_deploy_app` | — (read) | `appId` | the stored fields, `credentials: stored/none`, last deploy (time, result, SHA), webhook id if any. Never a token or secret. |
| `create_git_deploy_webhook` | `webhook.save` | `appId`, `provider` (`github`; `gitlab` later) | `webhookId`, `url` (`…/api/webhooks/{webhookId}`), `secret` (**once**) |
| `rotate_git_deploy_webhook_secret` | `webhook.rotate_secret` | `webhookId` | `secret` (**once**) |

Rules:

- `create_git_deploy_app` refuses an existing name (`conflict`) instead of overwriting.
- Owner (second amendment): `create_git_deploy_app`, `set_git_deploy_token` and `create_git_deploy_webhook` make the
  person who approved the call in Whiskers the owner of the app or webhook (R1-08) — or the caller, when a signed-in
  person calls; never the key, never a synthetic admin. A push later deploys on that person's authority, re-checked at
  each delivery; a key's own unattended runs fall under its agent rules (confirmation, tool list), which a deployment
  started by a push can never satisfy. A call with no person behind it (a policy that lets the key through unapproved)
  is refused with `denied` and changes nothing.
- `set_git_deploy_token` refuses a stale `revision` (`conflict`, R1-08).
- `create_git_deploy_webhook` creates a webhook with the action `git-deploy` bound to that app; the secret is
  generated by Whiskers (it cannot be supplied).
- Errors are MCP tool errors (`isError`) with a reason code: `invalid_argument`, `not_found`, `conflict`,
  `denied`, `pending_approval`, `failed`. *Clarification (review of BK-1):* this holds for all five tools and for
  what the gateway refuses before a tool runs (a stale revision is `conflict`, an unknown app `not_found`); the text
  is JSON `{"error": code, "message": …}` (`McpErrorEnvelope`).
- Read-back (INV-43): the save tools read the app back from the store; the webhook tools read the webhook back
  (existence, action, app binding). The token and the secret are not part of the read-back.

## Out of scope (after 1.0, unchanged from Brokkr's section 6)

Health check after deploy, rollback to a Git SHA, approval before a webhook deploy, a retrievable deploy history,
the `gitlab` provider, deleting apps or webhooks over MCP.

## Open points for acceptance

1. **Order:** Do this work package before R1-39 (proposal, because Brokkr is meant to be rolled out to all repos
   soon), or after R1?
2. **Approval policy for the Brokkr key:** keep the normal policy (a person approves each setup in Whiskers), or a
   dedicated guardrail preset for the Brokkr principal that allows exactly these capabilities without approval?
   Proposal: normal policy for v1. Setup is rare, and the approval is the human check before a new repository can
   deploy to a server.
3. **Tool names** as above (Brokkr adopts whatever Whiskers fixes).
